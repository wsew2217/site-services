Generic Site Services cost model

On-page guide for the product sandbox — not a single-customer deal. Sibling examples: Deal A (campus estate) · Deal B (tech bar). Methodology: Structure. Engine: engine/README.md.

Purpose

Primary economics sandbox for any estate. It prices structure and cost-shift (labor → logistics / OEM / zero-touch), not one contract’s campus count. Use it when the next deal should start from Site Services defaults and an engine summary — not by copying Deal A or Deal B numbers.

Inputs

  • Engine JSON — load /assets/engine-summary.json from python -m engine run … (see engine/README.md) when you need site-derived campuses and day-one techs. This is the deal-engine path.
  • VC Mapper bridge — preferred start for the VC kit: map → Cost_Model_Load → bridge; optionally run the engine on the bridged Sites file before uploading JSON here.
  • Intake assumptions — sites, users, tickets/user, physical-touch share, throughput, utilization, regional labor mix, logistics / dispatch / OEM / transition rates (editable placeholders).
  • Ratio bands — commercial guardrails on Scenarios (and Structure), not day-one sizing truth. Day one follows demand + VC floors.

Method

  • Engine pipeline — intake → demand → virtual campuses / staffing → overlays → scenarios → cost / cash JSON published for this page.
  • Interactive panes — Inputs (estate + rates + engine bridge) → Scenarios (ratio ladder, deflection, zero-touch) → Results (annual cost + composition) → Transition & Cash → Sensitivity → Model Logic (defensible formulas).
  • Road-map rungs size HC from users÷ratio floored by campuses×team floor; uncovered physical touches route to smart-hands and OEM.

How to use

  1. Open 1 . Inputs. Click Load sample engine summary (or upload a deal’s Deal_Output.json) so campuses and day-one techs stay reconciled.
  2. Refresh labor / logistics / OEM rates for the deal; leave structure defaults unless you have better evidence.
  3. On 2 . Scenarios, edit yellow cells (ratio, deflection, zero-touch, year reached). Keep the GOAL rung as the target for Sensitivity.
  4. Read 3 . Results for steady-state annual cost and the labor-to-logistics shift; use 4 . Cash for transition one-time and 7-year net vs as-is.
  5. Print / PDF exports the visible panes; Reset defaults restores the page snapshot. Rebuild engine outputs with the README quick-start, then re-copy JSON into /assets/.

Model logic (the defensible version)

Demand and staffing
  • Tickets/yr = users x tickets-per-user. Deflection% removes tickets before staffing (adoption of self-service and remote-first).
  • When an engine summary is loaded, day-one technicians and campus count come from the site/VC model (hub catchment + throughput). Manual Inputs remain a scenario sandbox.
  • Without an engine file, day-one technicians ≈ ceil(daily tickets x physical-touch share / on-site rate / utilization) + ceil(daily remote tickets / remote rate / utilization), floored by campuses x team floor.
  • Road-map rungs: technicians = max(campuses x floor, ceil(users / ratio)). Ratios are commercial guardrails, not the day-one sizing driver. Leads = ceil(techs/lead span); managers = ceil(techs/mgr span).
  • Blended tech rate = regional mix-weighted salary x (1 + burden). Leads at premium x blended; managers flat + burden.
Ops KPIs (delivery optimization)
  • Industry-typical ranges for deal QA — not customer truth. Full note: Structure → Delivery optimization metrics and engine/defaults/field_services_delivery_metrics.md.
  • Design band: utilization 85% (typical 75–85%), SLO 95%, FTFR target ≥85%, travel share <20% of workday, DOH green ≤1.5.
  • Deflection in this model is the commercial twin of avoidable-dispatch / remote-resolve (industry avoidable-dispatch median ~14%; ~1 in 5 cases remotely resolvable).
  • Failed first visits typically lift total resolution cost ~34–44% vs a single work order — which is why parts fill, remote triage, and FTFR matter as much as headcount.
Logistics, dispatch and OEM (the shift)
  • Physical touches = adjusted tickets x physical-touch share. Staff on-site capacity = techs x on-site allocation (60% of capacity) x rate x days x utilization.
  • Uncovered touches = max(0, touches - staff capacity): break-fix share of those goes to OEM warranty at attach% (per-event cost), the rest to smart-hands dispatch (per-visit cost).
  • Parts shipments = parts share of physical touches, costed per shipment; depots carry fixed + per-shipment variable; campus stock value x carrying% is inventory cost, scaled down as headcount consolidates (stock follows staffed footprint at 40% elasticity).
  • Device refresh = users x devices per user / refresh cycle. Zero-touch maturity% of refreshes ship direct (shipping only); the rest incur a touch cost plus shipping.
Transition and cash
  • Each step: exits x severance + hires x hire/training + parallel-run months x (old monthly labor x 25% overlap) + program management.
  • Cash view: each year charges the annual cost of the active rung plus any step one-time; cumulative line compares against staying at current state.
What this model deliberately is not

It is the generic Site Services cost model: it prices structure and shifts, not a specific contract. Reference Deal A (campus estate) lives at /cost-model-deal-a; Reference Deal B (tech-bar pattern, ~1500:1–2000:1) at /cost-model-deal-b. Site geography, hub selection, and VC floors live in the Python deal engine (python -m engine run). Load an engine summary JSON so campus count and day-one techs stay reconciled. Dollar rates are modern placeholders — refresh per deal (older PFS models inform structure only).

The ratio road map is a cost shift, not just a labor cut. This tool makes the shift visible and priceable.
