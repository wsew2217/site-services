## 1. Product framing

### What Site Services is
- **Site Services** and **Field Services** share the **same process-flow skeleton** (Future Mode of Operation / FMO). Commercial labels differ; the operating ladder does not.
- The product is a **methodology + deal engine + documentation suite** for designing deskside / field coverage for any estate from sparse site data.
- Day-one headcount is sized from **workload + geography**, not from a fixed users:tech myth. Users:tech ratios are **commercial guardrails / road-map rungs**, not the day-one driver.

## 3. Operating model (must recreate)

### FMO stage chain (inside the customer environment)
```
Intake → Misroute / QA → Remote? → Contact & schedule → Tower work → Logistics → Finalize
```
Process catalog pattern (FS001–FS021 style): initiation, mis-routed, contact & scheduling, hardware break/fix campus, hardware break/fix remote, repair/RMA, deskside software, new hire campus/remote, IMAC de-install / add-change / move, asset disposition, quarantine, data wipe, resolve, re-image, hot swap, shipping, Smart Hands, receiving, swivel-seat / partner dispatch.

Campus vs remote and partner dispatch are **routing overlays**, not separate methodologies.

Cadence defaults:
- Contact ≥ 2× per business day
- Incidents unreachable after ~3 business days / 3 attempts; requests after ~2 weeks
- Escalate after >2 misroute transfers
- Smart Hands: guided short tasks, **≤ ~60 min TOT** — not full break/fix
- Quarantine hold default **14** calendar days
- Close codes: RSLV / CNRC; status-code driven updates (DSCTM-style)

### Primary / Secondary / Tertiary role lanes
- Every tech has one **Primary** lane (home queue): Desktop-Incident, Desktop-Requests, Remote-Desktop, Staging, Site-Lead, Telecom, Network-VDI, Projects.
- **Secondary** / **Tertiary** = flex coverage labels — **not additive FTE**.
- Do not blend staging/infra throughput with deskside closure rates.
- Tickets assign by role, schedule, location, active load — not tech self-select.

### Virtual campus anatomy (hub-and-spoke)
- **Hub (Staffed)** — anchor maximizing catchment inside drive radius (default **~60 km / ~60 min**)
- **Local** — inside drive range; on-site reach
- **Remote** — outside range or no coordinates; remote queue + Smart Hands / OEM + shipping
- Every site belongs to **exactly one** campus (no orphans)
- Hub-led vs depot-led by on-site workload share; campuses promote/fold from rules + demand

### Tech bar / virtual tech / remote overlays
- On-site tech bar (walk-up)
- Virtual tech / remote desktop (resolve before dispatch)
- Remote resolution team (shift-left)
- Staging / depot (~25 mi campus staging; central depot for remote)
- Smart Hands / partner dispatch for physical touch when not local

### Staffing math (defaults)
- Working days: **252** · Utilization: **~85%** · Team floor: typically **2** (single-tech exception below ~2.5 tickets/day)
- On-site: **~6** incidents / tech / day, **~4** requests / tech / day
- Remote: **~5** tickets / tech / day
- Leads **1:10**, managers **1:24**
- Optional FMO calibration: ~**7** tickets / tech / day
- Demand when sparse: annual tickets → else users × estate rate → else devices × device rate → else placeholder + low-confidence flag
- Sites without coordinates stay Remote / Uncertain — never auto-Local

### Vertical ratio guidance (guardrails only)
| Pattern | Users : tech |
| --- | --- |
| Lean / mature | ~2000 : 1 |
| Healthcare | 250 : 1 – 750 : 1 |
| Manufacturing | 750 : 1 – 1000 : 1 |
| Administrative / office | 1000 : 1 – 1500 : 1 |
| Tech bar–heavy | 1500 : 1 – 2000 : 1 |

## 4. Delivery optimization metrics (required)

Surface on `/structure` as metric cards + deeper note in `engine/defaults/field_services_delivery_metrics.md`. Targets live under `ops_kpis.json` → `delivery_optimization`. Label everything **industry-typical**, not named-customer truth.

### Ranked deal-design KPIs
1. **First-time fix / first-visit resolution (FTFR)** — Design target **≥85%**. Industry median ~**75–77%**; top ~**86–88%**; bottom ~**53–60%**. Deskside first-visit avg ~**84%**. Prefer **30-day** related-ticket window.
2. **Avoidable dispatch / remote-resolve potential** — Industry median avoidable dispatch **~14%** (top ~**3%**, bottom ~**24%**). ~**1 in 5** cases remotely resolvable; ~**33%** of queries solvable without a field pro. Prices tech-bar / virtual / remote overlays.
3. **SLA / SLO attainment** — Suite internal **SLO 95%** (tighter than contractual SLA). Industry ops floors often ≥90%.
4. **Technician utilization** — Typical **75–85%**; suite designs at **85%**; pacesetters ~**90%**. Do not smash mid-80s at the expense of response slack.
5. **Travel vs wrench time** — Travel share target **<20%** of workday. Wrench time often **25–35%**; best-in-class **45–55%**.
6. **Cost per resolution / cost-to-serve** — Failed first visit lifts resolution cost **~34–44%** vs single work-order cost. Failed visits ≈ **25%** of service cost at median.
7. **Parts fill / logistics readiness** — Mature segmented discussion band **92–96%**.
8. **Schedule adherence** — Strong ops often **~85–90%+** on-time.
9. **Productivity & coverage ratios** — Suite throughputs above; users:tech = guardrails only.
10. **Backlog health (DOH) & aging** — DOH green **≤1.5**, amber **≤2.5**; aging bands 0–3 … 30+.
11. **CSAT / NPS / revisit / abandon** — CSAT often 80–85% “good”, 90%+ strong; abandon healthy ~2–5%.
12. **Dispatch / routing optimization** — Automation rate often **>80%** target; split KPIs by Campus / Local / Remote.

### Deal-design reading order
1. FTFR + avoidable dispatch + SLO  
2. Utilization band + throughput (HC); ratios stay guardrails  
3. Price remote / tech-bar deflection **before** cutting Local heads  
4. Show parts / depot / dispatch rising as labor falls (cost-to-serve shift)  
5. DOH / aging / CSAT as post-design QA — not day-one HC formula  

### `ops_kpis.json` highlights to carry
- `slo_target`: 0.95  
- `delivery_optimization.first_time_fix_rate_target`: 0.85  
- `avoidable_dispatch_rate_industry_median`: 0.14  
- `technician_utilization_design`: 0.85  
- `travel_share_of_workday_target_max`: 0.20  
- `resolution_cost_uplift_after_failed_first_visit_low/high`: 0.34 / 0.44  
- `doh_green_max` / `doh_amber_max`: 1.5 / 2.5  
- Smart Hands max TOT 60; reopen_days 15; productivity_closed_per_tech_day_target 5; fmo_tickets_per_tech_day_target 7

#### A) Generic Cost Model (`/cost-model`)
- **Purpose:** Primary economics sandbox for **any** estate. Prices structure and the labor→logistics shift; not a specific contract.
- **Inputs:** Sites, users, tickets/user, campuses (manual until engine loaded), physical-touch %, day-one on-site reach, throughput rates, utilization, team floor, lead/mgr spans, regional labor mix + burden, logistics/depot/stock, Smart Hands + OEM attach, current-state HC/logistics, transition costs. Optional load of `/assets/engine-summary.json` (or upload) locks campuses + day-one techs.
- **Method:** Tickets/yr = users × TPU; deflection removes tickets before staffing. Day one from engine when loaded; else ≈ on-site + remote throughput floors by campuses × team floor. Road-map rungs: max(campuses × floor, ceil(users / ratio)). Uncovered physical touches → OEM (break/fix share × attach) + Smart Hands. Parts/depot/stock + refresh (zero-touch vs touch+ship). Cash: current → day one (Y0) → rungs by “year reached” with severance/hire/parallel/PMO one-times.
- **Steps:** (1) Prefer Load sample engine summary or upload deal JSON. (2) Refresh dollar rates for the deal. (3) Set vertical ratio guardrails on Scenarios. (4) Edit yellow cells (ratio / deflection / zero-touch / year). (5) Read Results composition + Transition cash + Sensitivity tornado. (6) Open Model Logic for the defensible write-up.
- **What not to confuse:** Not Deal A’s 989-site truth; not Deal B’s tech-bar band. Does not pick hubs/VCs — that is `python -m engine run`. Dollar rates are modern placeholders. Ratios are guardrails, not day-one sizing.

#### B) Reference Deal A Cost Model (`/cost-model-deal-a`)
- **Purpose:** Economics for **one** campus-footprint example (~989 sites · 29 campuses · 114 day-one techs). Makes that estate’s cost shift priceable.
- **Inputs:** Same control surface as generic, but defaults + auto-load `engine-summary-deal-a.json` lock campuses/day-one techs to the example. Commercial rates remain editable placeholders. Dell OEM / lifecycle-hub lines are **attach opportunities in the cost-shift story**, not a claim that Site Services is a Dell program owned by the customer.
- **Method:** Same labor→logistics ladder as generic; day-one HC and campus count come from the published Deal A staffing/engine summary. Scenario ladder typically Current → Day one → 750 (goal) → 1000 → 1200 → 1500 with deflection/zero-touch maturity rising.
- **Steps:** (1) Confirm Deal A summary loaded (Reload if needed). (2) Keep estate-derived campuses/day-one unless exploring a sandbox. (3) Tune rates and scenario yellow cells. (4) Walk Results / Cash / Sensitivity. (5) Cross-link Structure metrics and Methodology appendix when briefing.
- **What not to confuse:** Not generic Site Services product defaults (`/cost-model`). Not Deal B. Dell Blue theme = vendor chrome on this example only. OEM warranty lines ≠ “Dell owns Site Services.”

#### C) Reference Deal B Cost Model (`/cost-model-deal-b`)
- **Purpose:** Economics for the **tech-bar walk-in + virtual** pattern (~65 offices · 8 bars · 13 day-one techs). Commercial band ~**1500:1–2000:1**.
- **Inputs:** Parallel UI, but “campuses” become **established tech bars**; floor = dedicated tech per bar. Auto-load `deal-b-tech-bar-summary.json`. Day-one = bar techs + dedicated virtual + roving. Depot/lifecycle hub is **logistics cost**, not bar headcount. No new bars proposed — coverage map for existing bars.
- **Method:** Day one demand-sized from walk-in + virtual queues (summary team 8+1+4). Road-map rungs **1500 (goal) / 1750 / 2000** with deflection & zero-touch. Same uncovered-touch → dispatch/OEM and parts/depot/stock logic, stocked per bar rather than per campus.
- **Steps:** (1) Confirm Deal B summary loaded. (2) Review bar count + day-one techs. (3) Edit rates and 1500–2000 rungs. (4) Read shift / cash / sensitivity. (5) Keep pattern brief (`/deal-b`) beside the model when presenting.
- **What not to confuse:** Not Deal A’s VC floors or 750:1 campus ladder. Not generic round-number sandbox. Depot lines ≠ tech-bar FTE. Day-one is bars+virtual+roving, not campus team floors.

## 6. Python deal engine (for Excel parity / HTML bridge)

```
python -m engine run <intake.xlsx> --out <deal.xlsx> [--json summary.json]
```

Modules: intake, demand, staffing (VC plan), dispatch, cost, ops, workbook. Defaults from `parameters.json` + `ops_kpis.json`. Cost-model pages consume the JSON summary so campus/bar counts and day-one techs stay reconciled with the site model.

## 10. Preferred VC kit pipeline (file path)

Preferred for new VC solutioning:

1. Fill `vc_template_pack_v1_0.xlsx` → tab `VC_Site_Input_Template` (one row per site).
2. Run `python vc_mapper.py` with `default_rules.yaml` → Hub / Local / Remote on `VC_Mapped_Sites` + Summary + `Cost_Model_Load` + Exceptions.
3. Run `python cost_model_bridge.py` → Sites intake xlsx + rough bridge JSON.
4. Optional full staffing: `python -m engine run <sites.xlsx> --out Deal_Output.xlsx --json Deal_Output.json`
5. Upload `Deal_Output.json` on `/cost-model` (Guide tab). Bridge JSON alone is a rough sandbox — prefer engine JSON for day-one lock.

### Dual tools
| Tool | Role |
| --- | --- |
| `python vc_mapper.py` | **Preferred** for this kit — roles + Cost_Model_Load |
| `python -m engine run` | Older / parallel full deal engine — Excel + Deal_Output.json |

Catchment rules (v1): Local ≤ **25 mi** OR ≤ 60 min @ 40 mph; near Staffed campus → **always Local**; Remote only if far **and** tpd < **1.2**; far ≥ 1.2 → Staffed; hub threshold 3.0 tpd.
